# 介质自带权限闸门：把可信边界做进设备

> companion to [ARCHITECTURE.md](ARCHITECTURE.md) · 本文讨论设计方向与技术可行性，
> 不涉及任何实施状态。参考实现中的设备后端是**接口演练**，不是真实硬件。

---

## 1. 问题：宿主 OS 的权限配置不是可信边界

如果允许执行者写日志的"开关"是宿主系统里的一项配置——文件 ACL、注册表只读位、
挂载参数——那么拥有足够权限的主体总能把它改回去。
**可配置状态不是不可绕过的边界。**

要真正做到"运行时执行者写不进账本"，闸门必须放在**被审计方改不到的地方**。
最直接的答案：放进可拔插介质自带的控制器里。

---

## 2. 先澄清一个概念

普通 U 盘是存储介质，没有可编程控制器，**跑不了"系统"**。
"在 U 盘上装一个权限闸门"落到工程上，只有三类形态：

| 形态 | 闸门驻留位置 | 能否分账号授权 | 宿主能否绕过 |
|---|---|---|---|
| **A · 文件系统 ACL** | 介质卷内的权限条目 | 可以（不同账号不同权限） | **可以**——取得所有权即可改回 |
| **B · 宿主策略 / 驱动层** | 注册表只读位、组策略、挂载参数 | 部分 | 用户态绕不过，但需要管理员设置，且不随介质走 |
| **C · 设备固件** | 设备控制器：只暴露 append 接口，不暴露块写口 | 可以（设备验请求方凭证） | **不行**——宿主最高权限也只能走设备公开的接口 |

**只有形态 C 把可信边界真正移出了宿主。**

形态 A 仍有价值，但它的定位是"纵深防御的一层"，不是"系统级拒写的证据"。
这与 [AVIATION_LESSONS.md](AVIATION_LESSONS.md) 中"操作系统只读是可逆、可解除、易绕过的"
这一现实判断一致。

---

## 3. 形态 C 不是构想：现有技术路线

### 3.1 WORM 存储是成熟品类

WORM（Write Once Read Many，一次写入多次读取）设备在硬件或固件层锁定数据，
写入后不可修改或删除；商用产品覆盖存储卡与 USB 设备，配审计追踪与错误校验，
部分形态符合长期归档的合规标准（如 SEC Rule 17a-4(f)、FDA 21 CFR Part 11）。

公开的技术分类把 WORM 分为**物理型 / 固件型 / 软件型**——
并明确指出：操作系统与文件系统提供的只读是"可逆、可解除、易绕过"的，
不满足 WORM 所需的强固性。这与第 2 节的判断一致。

### 3.2 开源等价路线

一个公开的学术方案（*The Reverse File System* / Socarrat）给出了低成本实现：

- 用一块运行 Linux、支持 USB OTG 的单板机作为 USB 设备；
- 宿主看到的是普通 ext4/exFAT 磁盘，无需专用驱动；
- 设备在块层解析宿主写来的数据块，"逆向"推断上层文件操作，
  **只对受保护日志文件的追加放行，丢弃一切改写**；
- 设计目标是"即使具有特权控制的攻击者也无法修改或擦除数据"。

工程难点是宿主与设备不能同时挂载同一分区，需要通过网络块设备协议导出块卷，
并解析文件系统内部结构（inode、extent、journal）。有门槛，但并非不可行。

### 3.3 航空先例

真实飞行记录器本身就是"处理器 + 固化固件 + 受限存储"的设备，
不是裸盘，也不跑通用操作系统——这与形态 C 是同一思路：
**功能越固化，写入端越没有裁量权，可信边界越清晰。**

## 4. 按证据强度分层投入

一刀切给所有记录上最强硬件闸门是浪费。两本账的证据强度本就不同：

- **声明账**（主体自述）：本就属弱证据，其"不可信"是已声明的产品边界；
  随介质 ACL 防护即可，被绕过的风险在边界内。
- **执行账**（实际行为）：强证据端，承载"言行差额"的核心判定；
  闸门放进设备固件，才配得上它的证据角色。

**分别授权**：声明账写入凭证只允许写声明账；执行账写入凭证经设备验签后才被放行追加；
对照类角色对两账只读、连追加都不给。
上层对照与重放逻辑无需改动——只需把"进程内 token"升级为"设备验签凭证"。

## 5. 软件先行：接口适配可以在没有硬件时完成

等待设备到位期间，软件层可以做**接口演练**，把未来接入成本降到最低：

1. **定义最小设备契约**：`append(payload) → entry`、`read_all()`、`head()`、`verify()`。
   四个方法就是设备固件该实现的全部接口面——接口越小，攻击面越小。
2. **两种后端**：文件后端包装现有实现（行为完全一致）；
   设备模拟后端演练设备语义（保留字段拒收、单调序号、设备签名形状、篡改检出）。
3. **契约测试**：同一组输入喂两个后端，`seq` / `prev_hash` / `entry_hash` 逐条同构，
   两后端整链校验都通过；再单独测设备特有的拒改写与验签。

**必须写死的诚实边界**：
设备模拟后端是 `simulated` 的——它证明**软件架构能适配**，不是"设备已防篡改"。
证据强度由硬件闸门决定，不由软件适配决定。
**接口演练完成，不等于任何隔离判据达成。**

## 6. 残余风险（有限深度）

- 设备固件本身成为新的可信主体：固件有缺陷或后门怎么办？
  靠固件开源可审计 + 外部复算交叉验证来抬高成本，不假装解决。
- 验签密钥的分发若由实现方独控，又回到自证——需要独立的认定机制。
- 物理攻击始终存在：写保护开关可被破坏、策略可被篡改。
  **没有任何单一措施绝对安全**；多层叠加 + 独立见证才是方向。
- 通用原则：**写"提高造假成本"，不写"防住"**。

---

## 7. 小结

1. 宿主 OS 的权限配置不适合作为可信边界；设备固件才是。
2. 形态 C 有成熟技术先例（WORM 品类、开源块层 append-only 方案、航空记录器）。
3. 按证据强度分层：弱证据端软件防护，强证据端硬件闸门。
4. 软件接口适配可先行，但模拟不等于证据——诚实标注 `simulated`。
5. 有限深度：每一层都抬高成本，没有一层宣称绝对可信。
